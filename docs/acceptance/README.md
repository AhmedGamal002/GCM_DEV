# دليل الاختبار وقبول التنفيذ — Testing & Acceptance

الهدف: تقدر — كمدير نظام أو مالك منتج — تتأكد إن **كل ميزة اتنفذت زي ما الـ FRD طالبها**، بخطوتين:

1. **الاختبارات الآلية** — تشغيلة واحدة تثبت إن المنطق الداخلي (الصلاحيات، العزل بين الشركات، قواعد العمل) شغّال.
2. **قوائم القبول اليدوية** — تمشي عليها بالماوس والكيبورد، كل بند = خطوة + نتيجة متوقعة + مرجع الـ FRD.

---

## أولًا: الاختبارات الآلية

من جذر المشروع:

```bash
php artisan test
```

- **كل التستات لازم تعدي خضراء** — أي `FAIL` معناه ميزة مكسورة، متكملش قبول يدوي قبل ما تتصلح.
- عدد التستات الحالي وتغطيتها مذكورة في `CLAUDE.md` (قسم "الحالة الحالية") و`WEEKLY_PLAN.md`.
- لتشغيل تستات موديول واحد بس: `php artisan test --filter=Vehicle` (أو `Driver` / `Asset` / `User` / `MenuVisibility` / `Platform`).
- التستات بتشتغل على قاعدة بيانات SQLite في الذاكرة — **مش بتلمس** قاعدة بياناتك المحلية (`gcm_dev`).

### إيه اللي الاختبارات الآلية بتغطيه فعليًا

| المجال | أمثلة |
|---|---|
| **العزل بين الشركات** | مدير نظام في شركة A مبيقدرش يوصل لأي صف بيانات في شركة B (بيرجع 404 مش 403) |
| **الصلاحيات لكل دور** | كل دور بيرجع 403 على اللي ممنوع منه؛ auditor عرض بس؛ data_entry من غير تعطيل؛ إلخ |
| **قواعد العمل من الـ FRD** | مدير نظام واحد لكل شركة · تعطيل مدير النظام ممنوع دايمًا · المركبة الافتراضية لسائق واحد · تعديل الأصل الاسم فقط · إلخ |
| **الترقيم والبحث السيرفر-سايد** | `per_page` صغير بيرجّع العدد الكلي الصح · البحث بيلاقي بالقيمة المعروضة · الفرز `desc` فعليًا بيعكس |
| **رفع وتحميل المستندات** | مستندات السائق بتتخزن خاصة (مش `public`) وبتترجع بس عن طريق رابط محمي |
| **التصدير** | Excel و PDF بيرجعوا ملف فعلي بالأعمدة الصح |

> **الاختبارات الآلية مش بتغطي:** الشكل البصري، تجربة المستخدم، الترجمة، سلامة الـ breadcrumb، سلوك المتصفح الحي — دي كلها في قوائم القبول اليدوية.

## ثانيًا: قوائم القبول اليدوية

| الملف | يغطي |
|---|---|

### الطريقة الأسهل: `checklist.html`

افتح **`docs/acceptance/checklist.html`** في أي متصفح (دبل كليك) — فيه كل بنود الملفات دي في صفحة واحدة: تجهيز البيئة، الحسابات، وكل بند بخطواته ونتيجته المتوقعة. علّم ✔ على اللي خلّصته أو "فشل" واكتب ملاحظة؛ التقدّم بيتحفظ في المتصفح، وزر **نسخ تقرير النتيجة** بيجمّع الفاشل مع ملاحظاته عشان تبعته للمطوّر. الملف **بيتولّد** من ملفات `week-*.md` — بعد أي تعديل عليها: `node docs/acceptance/build-checklist.mjs` (متعدّلش الـHTML بإيدك).

### نسخة العميل: `client-checklist.html`

**نفس السكريبت** (`node docs/acceptance/build-checklist.mjs`) بيولّد كمان **`docs/acceptance/client-checklist.html`** — نسخة منفصلة تتبعت للعميل نفسه يختبر بيها، فيها فرق جوهري عن نسخة `checklist.html` بتاعتنا:

- **مقصورة على اللي مدير النظام لوحده يقدر يختبره** — أي بند أصلي كان محتاج تسجيل دخول بحساب تاني (data_entry/auditor/driver)، أو شركة تانية، أو Super Admin، أو Postman، اتشال أو اتقصّر لجزئه اللي مدير النظام يقدر يجربه لوحده.
- **منظّمة موديول بموديول (Users → Drivers → Vehicles → Vehicle Categories → Assets → Asset Categories)، مش بترتيب اكتشاف الفجوات** زي ملفات المصدر — جوه كل موديول الترتيب ثابت: عرض → إنشاء → تعديل → تغيير حالة → قواعد عمل إضافية، عشان الـtester يقدر يشوف "خلّصت الـCRUD كله للموديول ده؟" بنظرة واحدة. بعد الموديولات فيه 3 أقسام عامة (قواعد عبر الموديولات، الواجهة والتنقل، الأداء والتصدير) للحاجات المشتركة اللي مش تخص موديول واحد بعينه.
- **`CLIENT_GROUPS`** (مش `CLIENT_INCLUDE` القديمة) — array بترتيب الأقسام والبنود جوه كل قسم صراحة، وهو الـallowlist والترتيب في نفس الوقت: أي بند جديد تضيفه لأي `week-*.md` **مش هيظهر في نسخة العميل تلقائيًا** لحد ما تراجعه وتضيف الـid بتاعه (`<اسم-الملف>#<رقم البند>`) للقسم المناسب جوه `CLIENT_GROUPS` — لو الـid غلط أو البند اتشال من المصدر، السكريبت بيرمي error فورًا (مش بيسيب البند يختفي بصمت). لو محتاج تبسيط في النص (خطوات/نتيجة متوقعة/FRD/العنوان) ضيفه في `CLIENT_OVERRIDES` زي الأول.
- **لاحظت الموديولات ناقصة "تعديل"/"تغيير حالة" كبنود مستقلة رغم إن الـCRUD شغّال ومتغطّى بالتستات؟** كانت فعلاً ناقصة كبنود *قبول يدوي* (مش كتغطية آلية) — 7 بنود جداد اتضافوا (تعديل + تغيير حالة لمستخدم/سائق، تعديل مركبة، إنشاء أصل + تغيير حالته) في نهاية `week-1-2-auth-users-roles.md` و`week-3-vehicles-drivers-assets.md` (أقسام "و)"/"هـ) استكمال CRUD" — عشان منكسرش ترقيم موجود).
- **مفيش أي أثر إنها اتولّدت آليًا** — بدون "آخر مزامنة FRD"، بدون "يغطيه آليًا" (أسماء كلاسات التستات)، بدون ذكر أسبوع/مرحلة، بدون فوتر "اتولّد من...". بدل ما تعطي بيانات كل الحسابات، أول الصفحة بيدّي رابط + إيميل + باسورد مدير النظام بس عشان يبدأ يختبر فورًا.
- **زر "تصدير Excel"** بدل "نسخ تقرير النتيجة" — بيبني ملف `.xls` حقيقي (SpreadsheetML، بيتفتح في Excel من غير أي إضافة) فيه القسم/الرقم/البند/الحالة/الملاحظات لكل بند، ومحفوظ محليًا بره أي localStorage مشترك مع نسخة الأدمن.

**لو غيّرت الرابط/الإيميل/الباسورد** (مثلاً بيئة نشر جديدة)، عدّل قسم "بيانات الدخول" جوه الـtemplate بتاع `client-checklist.html` في السكريبت نفسه، مش الـHTML الناتج.

### إزاي تمشي على قائمة قبول (يدويًا من الـmarkdown)

1. **حضّر بيانات نظيفة:** `php artisan migrate:fresh --seed` (بيصفّر `gcm_dev` ويزرع: شركة GCM + الحسابات التجريبية الأربعة + بيانات مرجعية).
   - الحسابات: `admin@gcm.test` / `dataentry@gcm.test` / `auditor@gcm.test` / `driver@gcm.test` — كلهم كلمة السر `password`.
   - Super Admin: `superadmin@product.test` / `password` على `/platform/login`.
2. شغّل السيرفر: `php artisan serve` وافتح `http://localhost:8000`.
3. لكل بند في القائمة: نفّذ **الخطوات**، قارن بـ**النتيجة المتوقعة**، وعلّم ✅ / ❌.
4. أي ❌ → افتح الملف، اكتب اللي حصل فعليًا جنب البند، وارجع للمطوّر بالبند + رقم قسم الـ FRD.
5. آخر الجلسة: `php artisan migrate:fresh --seed` تاني عشان ترجّع الداتا نضيفة.

### شكل البند الموحّد

```
### [رقم] عنوان البند
- **FRD:** §x.y.z (اسم القسم في المستند)
- **الدور:** بأي حساب تسجّل دخول
- **الخطوات:** 1) ... 2) ... 3) ...
- **النتيجة المتوقعة:** ...
- **يغطيه آليًا:** TestClassName::test_method (أو "يدوي فقط")
- **النتيجة:** ⬜ لسه / ✅ عدى / ❌ (اكتب اللي حصل)
```

## مزامنة الـ FRD — دايمًا آخر نسخة

- المرجع الفعلي هو **أحدث ملف `.docx` في جذر المشروع** — حاليًا **`GCM_Portal_NewSystem_FRD_V01.09.docx`** (بتاريخ 2026-09-01).
- كل ملف قبول في رأسه سطر `> آخر مزامنة: FRD V01.09`.
- **لما تنزل نسخة `.docx` أحدث:**
  1. استخرج نصها (فك الضغط كـ zip → `word/document.xml` → parse — النص العربي في الـ PDF مش قابل للاستخراج، لازم الـ docx).
  2. قارن الأقسام المتغيّرة (خصوصًا جداول الصلاحيات وعناصر الفورم).
  3. حدّث البنود المتأثرة في ملفات القبول + رقم النسخة في الرأس.
  4. لو تغيّرت قاعدة عمل: حدّث الكود والتست الآلي **قبل** ما تقفل بند القبول.
